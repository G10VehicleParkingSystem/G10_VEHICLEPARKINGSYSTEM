# Deviations from the Submitted Documents

This file records where the final build (v1.0, tagged 19-Nov-2026) differs from
the submitted SRS (v1.0, 04-Sep-2026), SAD and Software Test Plan (v1.0,
16-Sep-2026), as required by item 2(i) of the Mini-Project Deliverables. Each
deviation will be explained during the final demo.

D-1 to D-9 were first recorded after Sprint 1; the "Status in v1.0" column says
how each one ended. D-10 to D-12 were added in Sprint 2 and Sprint 3.

| # | Document reference | Planned | What was built | Reason | Status in v1.0 |
|---|---|---|---|---|---|
| D-1 | SRS 6.3, 6.5; REQ-1, REQ-4, REQ-8; Test Plan VPS-F-001, VPS-NF-004, 5.1 | Users register and log in; passwords are hashed; admin-only actions are role-restricted | Sprint 1 had no authentication: endpoints took `userId` in the body/query and admin endpoints were open | Sprint 1 focused on the seven functional modules so each owner could work independently against a shared contract | **Resolved** in PR #50 (18 Nov): `src/modules/auth` adds users with bcrypt-hashed passwords, JWT login, middleware that takes the user from the token instead of `userId`, admin-only routes, and per-user access to records and vehicles. Tested by TC-AUTH-01..11 and TC-SEC-01..12 |
| D-2 | SRS 2.4, 3.1, 3.2; SAD front-end layer; Test Plan section 6 | React front end with login, vehicle, reservation, payment, tracking and admin dashboard screens | Sprint 1 was back end only, exercised through the REST API | Back-end business rules were prioritised so the UI could be built against stable APIs | **Resolved** in PR #49 (15 Nov) and PR #50: the CampusPark React front end in `frontend/`, with sign-in, served by the backend from the same port |
| D-3 | SRS 3.2; REQ-8 | Payment gateway in sandbox/test mode | `DEMO_GATEWAY` simulates successful payments (`PAYMENT_GATEWAY=demo`); any other setting records a failed payment | No external provider account is available; card data is never collected, which also satisfies the "no raw card details" rule | **Kept.** The live site also runs with the demo gateway. TC-SEC-12 confirms no card fields are stored |
| D-4 | SRS 5.4, 5.5 | Parking sessions start when a vehicle arrives | Sessions start and end through `POST /api/parking/check-in` and `POST /api/overstays/:reservationId/checkout` | No parking hardware in scope (SRS 2.1, Test Plan section 4) | **Kept.** In the web app these are the "I've arrived" and "I'm leaving" buttons; the QR gate pass (D-10) identifies the vehicle |
| D-5 | REQ-15 | Overstay detected while the vehicle is still parked | Detection runs every `OVERSTAY_CHECK_INTERVAL_MS` (default 60 s) on confirmed reservations past their end time, whether or not the vehicle checked in | Reservations are the source of truth for the allowed time without hardware sensors | **Kept** after review in Sprint 2. The office can also run detection on demand ("Check for overstays now") |
| D-6 | REQ-22 | Notify before an upcoming reservation and before parking expires | Reminders are sent `UPCOMING_REMINDER_MINUTES` (default 30) before start and `EXPIRY_REMINDER_MINUTES` (default 15) before end; in-app only | SRS 3.3 limits this version to in-app notifications | **Kept.** A merge on 11 Nov had stopped reminders from being sent (DEF-01); fixed in PR #50 |
| D-7 | Test Plan section 7 | Test milestones 18-Sep to 28-Sep-2026 | Testing ran inside the sprints: Sprint 1 (19-23 Oct), Sprint 2 (26-30 Oct, with carried-over work finished in November) and a dedicated testing sprint, Sprint 3 (16-20 Nov) | The Deliverables brief, issued after the Test Plan, fixed the sprint calendar; Sprint 2 work (front end, login, FR-8, FR-9) took longer than one week | **Closed.** All planned tests executed; see [reports/TEST_SUMMARY_REPORT.md](reports/TEST_SUMMARY_REPORT.md) |
| D-8 | Test Plan sections 5 (integration, performance) and 6 (tools) | Integration tests across front end, back end, DB and payment interface; performance measured with tools such as Postman | Sprint 1 had only unit tests with the database stubbed, and manual end-to-end checks | No front end and no test database in CI at the time | **Resolved** in PR #51: a black-box suite (`tests/blackbox/run-blackbox.mjs`, 87 cases) runs against a real server and MongoDB in CI, with coverage (c8) and response times (TC-PERF-01..04). Automated runners replace manual Postman runs. The React front end was tested by hand, not with automated browser tests |
| D-9 | REQ-6 | Cancelling a reservation "releases the slot back to the available pool" | A cancelled reservation no longer blocks that time window. Slot `status` reflects physical occupancy and changes only on check-in/checkout | A slot can hold many future reservations, so a single status field cannot represent bookings | **Kept.** TC-RES-12 checks that a cancelled time can be booked again |
| D-10 | SRS 3.1 (scope), SAD component list | Seven functional requirements (FR-1 to FR-7) | Three features beyond the SRS: **FR-8** monthly reserved parking subscription (PR #40), **FR-9** slot reviews and ratings (PR #42, #44, #45), and a **QR gate pass** for vehicle identification (PR #46) | Added by the team during Sprint 2 as extensions for campus use; they build on FR-1 to FR-7 without changing them | **Added.** Each has unit tests and black-box cases (TC-SUB, TC-REV, TC-VEH-01, 09) |
| D-11 | Test Plan section 4 ("cloud hosting and public-domain deployment" not tested); SAD deployment view | Local deployment only | The system is deployed on Render (free plan) with MongoDB Atlas, through a CI/CD pipeline: `ci.yml` checks every change; `cd.yml` publishes a Docker image, deploys it, waits for it to go live and smoke tests the live site | A public URL lets the examiners and the team use the same running system | **Added.** Live at https://g10-parking.onrender.com. The free plan sleeps after 15 minutes without visitors, so the first request then takes about a minute |
| D-12 | REQ-5, Test Plan VPS-NF-005 | Overlapping reservations are prevented | The overlap check and the insert were separate steps, so simultaneous requests could double-book a slot (DEF-02, found by TC-RES-14 in Sprint 3) | Not covered by the original design | **Resolved** in PR #51: a short per-slot booking lock, taken with one atomic MongoDB update, makes the check and the insert run one request at a time per slot |
