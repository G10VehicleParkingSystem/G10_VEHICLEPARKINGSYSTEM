# Deviations from the Submitted Documents

This file records where the Sprint 1 build differs from the submitted SRS
(v1.0, 04-Sep-2026), SAD and Software Test Plan (v1.0, 16-Sep-2026), as
required by item 2(i) of the Mini-Project Deliverables. Each deviation will be
explained during the final demo.

| # | Document reference | Planned | Sprint 1 build | Reason | Plan |
|---|---|---|---|---|---|
| D-1 | SRS 6.3, 6.5; REQ-1, REQ-4, REQ-8; Test Plan VPS-F-001, VPS-NF-004, 5.1 | Users register and log in; passwords are hashed; admin-only actions are role-restricted | No authentication. Endpoints take `userId` in the body/query, and admin endpoints (`/api/analytics`, `/api/overstays/detect`, `POST /api/slots`) are open | Sprint 1 focused on the seven functional modules so each owner could work independently against a shared contract | Sprint 2: user model with hashed passwords, login with tokens, auth middleware replacing `userId` parameters, admin role checks |
| D-2 | SRS 2.4, 3.1, 3.2; SAD front-end layer; Test Plan section 6 | React front end with login, vehicle, reservation, payment, tracking and admin dashboard screens | Back end only; features are exercised through the REST API (Postman/curl) | Back-end business rules were prioritised so the UI could be built against stable APIs | Sprint 2: React front end consuming the existing endpoints |
| D-3 | SRS 3.2; REQ-8 | Payment gateway in sandbox/test mode | `DEMO_GATEWAY` simulates successful payments locally (`PAYMENT_GATEWAY=demo`); any other setting records a failed payment | No external provider account is available for the demo; card data is never collected, which also satisfies the "no raw card details" rule | Keep the demo gateway; swap `payment.gateway.js` for a provider sandbox if time permits |
| D-4 | SRS 5.4, 5.5 | Parking sessions start when a vehicle arrives | Sessions start through `POST /api/parking/check-in` and end through `POST /api/overstays/:reservationId/checkout`, both triggered manually | No parking hardware in scope (SRS 2.1, Test Plan section 4) | None; the endpoints stand in for gate events |
| D-5 | REQ-15 | Overstay detected while the vehicle is still parked | Detection runs every `OVERSTAY_CHECK_INTERVAL_MS` (default 60 s) on confirmed reservations past their end time, whether or not the vehicle checked in | Reservations are the source of truth for the allowed time without hardware sensors | Review in Sprint 2 once check-in is driven from the UI |
| D-6 | REQ-22 | Notify before an upcoming reservation and before parking expires | Reminders are sent `UPCOMING_REMINDER_MINUTES` (default 30) before start and `EXPIRY_REMINDER_MINUTES` (default 15) before end, polled on the same interval as overstay detection; delivered in-app only | SRS 3.3 limits this version to in-app notifications | None |
| D-7 | Test Plan section 7 | Test milestones 18-Sep to 28-Sep-2026 | Testing ran inside the sprints set by the Deliverables brief: Sprint 1 (19-23 Oct) and Sprint 2 (26-30 Oct) | The Deliverables brief, issued after the Test Plan, fixed the sprint calendar | Remaining UAT, security and usability testing in Sprint 2 |
| D-8 | Test Plan section 5 (integration, performance) | Integration tests across front end, back end, DB and payment interface; performance measured with tools | Automated unit tests stub the database (`npm test`, run in CI). Integration was verified manually end-to-end against a local MongoDB; response times were spot-checked with curl on a small dataset (all under 25 ms) | No front end yet; CI has no MongoDB service | Sprint 2: API integration tests against a test database and timing with realistic data |
| D-9 | REQ-6 | Cancelling a reservation "releases the slot back to the available pool" | A cancelled reservation no longer blocks that time window. Slot `status` reflects physical occupancy and changes only on check-in/checkout | A slot can hold many future reservations, so a single status field cannot represent bookings | None |
